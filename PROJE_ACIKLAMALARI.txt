STAJ API - KURULUM, PROJE YAPISI, YAPILANLAR VE TEST REHBERİ
================================================================

Bu dosya projeyi başka bir bilgisayarda çalıştırmak, yapılan işleri
anlamak ve bütün özellikleri test etmek için hazırlanmıştır.

Güncel çalışma branch'i:

    feature/user-pagination

Bu branch; PostgreSQL, Entity Framework Core, User CRUD, validation,
Swagger, şifre hashleme, JWT, Postman koleksiyonu, kullanıcı arama ve
sayfalama çalışmalarının tamamını içerir.


1. PROJENİN AMACI
-----------------

Bu proje .NET 10 ile geliştirilmiş bir ASP.NET Core Web API projesidir.
MVC görünümü veya HTML sayfası yoktur. İstemciler API'ye HTTP istekleri
gönderir, API de çoğunlukla JSON cevap verir.

Projede iki bölüm vardır:

1. Stajyer işlemleri
   İlk öğrendiğimiz basit, bellek içi CRUD örneğidir. Uygulama yeniden
   başlatılınca sonradan eklenen stajyerler silinir.

2. User işlemleri
   PostgreSQL ve Entity Framework Core kullanır. Veriler veritabanında
   kalıcıdır. User CRUD, validation, şifre hashleme, login, JWT,
   pagination ve search özellikleri burada bulunur.

Kullanılan teknolojiler:

- .NET 10 / ASP.NET Core Web API
- C#
- PostgreSQL 17
- Docker Desktop
- Entity Framework Core 10
- Npgsql PostgreSQL provider
- Swagger / OpenAPI
- Postman
- DBeaver
- JWT Bearer Authentication
- ASP.NET Core PasswordHasher

7. İSTEK PROJEDE NASIL İLERLİYOR?
---------------------------------

Örnek bir POST isteğinin yolu:

İstemci / Postman / Swagger
    -> HTTP isteği
    -> Routing
    -> Model Binding
    -> Model Validation
    -> UserController
    -> IUserService

8. KLASÖR VE DOSYALARIN GÖREVİ
------------------------------

Program.cs
    Uygulamanın başlangıç dosyasıdır. Controller, DbContext, service,
    JWT, Swagger, authentication, authorization ve exception handler
    burada kaydedilir. HTTP pipeline sırası da burada kurulur.

Controllers/
    HTTP isteklerini karşılar.

    UserController.cs
        User CRUD, pagination ve search endpointleri.

    AuthController.cs
        Login ve JWT doğrulama endpointleri.

    StajyerlerController.cs
        İlk öğrenme aşamasındaki bellek içi stajyer CRUD örneği.

Services/
    İş kuralları ve veritabanı işlemleri burada yürütülür.

    UserService.cs
        Kullanıcı listeleme, arama, tekil get, create, update ve delete.

    AuthService.cs
        Şifre doğrulama, JWT üretme ve claimleri response'a çevirme.

Services/Interfaces/
    Service sözleşmelerini tutar.

    IUserService.cs
        UserService'in uygulamak zorunda olduğu metotları belirler.

    IAuthService.cs
        AuthService'in uygulamak zorunda olduğu metotları belirler.

Models/Entities/User.cs
    PostgreSQL'deki Users tablosunu temsil eden Entity'dir.

Models/Requests/
    API'ye gelen verilerin şeklidir.

    UserCreateModel.cs
        Name, Email, Password alır. ID istemciden alınmaz.

    UserUpdateModel.cs
        Yalnızca Name alır. ID ve Email değiştirilemez.

    LoginRequest.cs
        Email ve Password alır.

    UserListQuery.cs
        Page, PageSize ve isteğe bağlı Search query değerlerini alır.

Models/Responses/
    API'nin dışarıya döndürdüğü güvenli cevap modelleridir.

    UserDto.cs
        Id, Name ve Email döndürür. PasswordHash dışarı çıkmaz.

    PagedResponse.cs
        Items, Page, PageSize, TotalCount ve TotalPages bilgilerini tutar.

    LoginResponse.cs
        JWT, token türü ve sona erme zamanını döndürür.

    TokenValidationResponse.cs
        Token geçerliyse kullanıcı ve claim bilgilerini döndürür.

data/AppDbContext.cs
    EF Core ile PostgreSQL arasındaki bağlantıyı ve Users tablosunun
    kurallarını tanımlar.

data/AppDbContextFactory.cs
    Migration komutları çalışırken DbContext oluşturur ve ayarları okur.

Exceptions/

ExceptionHandling/GlobalExceptionHandler.cs
    Service'ten gelen exception'ları uygun HTTP durum koduna ve sade
    JSON hata mesajına dönüştürür.

Migrations/
    Veritabanı şemasındaki değişikliklerin kodla tutulduğu geçmiş.

postman/StajApi.postman_collection.json
    Hazır Postman istekleri, değişkenleri ve otomatik testleri içerir.

swagger.json
    API'nin güncel OpenAPI belgesinin repo içindeki kopyasıdır.

docs/swagger.png
    Swagger ekran görüntüsüdür.


9. INTERFACE, SERVICE VE DEPENDENCY INJECTION
--------------------------------------------

Interface, bir sınıfın hangi metotları sunması gerektiğini belirleyen
sözleşmedir. Metodun nasıl çalışacağını değil, imzasını söyler.

IUserService içindeki güncel metotlar:

    Task<PagedResponse<UserDto>> GetAllAsync(UserListQuery query)
    Task<UserDto> GetByIdAsync(string id)
    Task<UserDto> CreateAsync(UserCreateModel model)
    Task<UserActionResponse> UpdateAsync(Guid id, UserUpdateModel model)
    Task DeleteAsync(Guid id)

UserService : IUserService yazdığı için bu sözleşmeyi uygular.

Dependency Injection, ihtiyaç duyulan nesnenin sınıf içinde `new` ile
üretilmek yerine dışarıdan verilmesidir. Program.cs içindeki kayıt:

    builder.Services.AddScoped<IUserService, UserService>();

Controller constructor'ında IUserService ister. ASP.NET Core her HTTP
isteği için uygun UserService nesnesini verir.

Scoped lifecycle, aynı HTTP isteği boyunca aynı service/DbContext
örneğinin kullanılması; başka istekte yeni örnek oluşturulmasıdır.


10. USER ENDPOINTLERİ
---------------------

1. Listeleme, sayfalama ve arama

    GET /api/User?Page=1&PageSize=10&Search=kaan

Search zorunlu değildir. Name veya Email içinde büyük/küçük harf
duyarsız arama yapar. Request body kullanılmaz; değerler query string
ile gelir.

Başarılı cevap: 200 OK

{
  "items": [
    {
      "id": "11111111-1111-1111-1111-111111111111",
      "name": "Fatih",
      "email": "fatih.ulus@pointr.tech"
    }
  ],
  "page": 1,
  "pageSize": 10,
  "totalCount": 1,
  "totalPages": 1,
  "hasPreviousPage": false,
  "hasNextPage": false
}

2. Tek kullanıcı

    GET /api/User/{id}

Örnek:

    GET /api/User/11111111-1111-1111-1111-111111111111

Geçersiz GUID: 400 Bad Request
Geçerli formatta olup bulunmayan GUID: 404 Not Found
Bulunan kullanıcı: 200 OK

3. Kullanıcı oluşturma

    POST /api/User

Request body:

{
  "name": "Test Kullanıcı",
  "email": "test.kullanici@example.com",
  "password": "Password123!"
}

Başarılı: 201 Created
Geçersiz alanlar: 400 Bad Request
Aynı email: 409 Conflict

ID, API içinde `Guid.NewGuid()` ile otomatik üretilir. UserType otomatik
olarak `User` olur. Düz şifre veritabanına yazılmaz.

4. Kullanıcı adı güncelleme

    PUT /api/User/{id}

Request body:

{
  "name": "Yeni İsim"
}

Modelde sadece Name olduğu için ID ve Email request body ile
değiştirilemez. Başarılı cevap 200 OK ve mesajdır:

{
  "message": "User \"GUID\" updated"
}

5. Kullanıcı silme

    DELETE /api/User/{id}

Başarılı: 204 No Content
Kullanıcı yoksa: 404 Not Found


11. AUTH VE JWT ENDPOINTLERİ
----------------------------

1. Login

    POST /api/Auth/login

Request body:

{
  "email": "test.kullanici@example.com",
  "password": "Password123!"
}

AuthService email ile kullanıcıyı bulur ve PasswordHasher ile girilen
şifreyi veritabanındaki hash'e karşı doğrular. Email veya şifre yanlışsa
401 Unauthorized döner. Doğruysa 200 OK ile JWT döner.

2. JWT doğrulama

    GET /api/Auth/validate

Header:

    Authorization: Bearer JWT_TOKEN

Geçerli token: 200 OK
Eksik, bozuk veya süresi geçmiş token: 401 Unauthorized

JWT içine eklenen claimler:

- sub: kullanıcının GUID değeri
- jti: tokenın benzersiz kimliği
- name: kullanıcı adı
- email: kullanıcı emaili
- type: User
- role: User

`[Authorize]` attribute'u validate endpointine yalnızca geçerli tokenla
ulaşılmasını sağlar.


12. ŞİFRE HASHLEME
------------------

Kullanıcının yazdığı düz şifre saklanmaz. Create sırasında:

    _passwordHasher.HashPassword(user, model.Password)

ile hash üretilir ve PasswordHash alanına yazılır.

Aynı şifre farklı kullanıcılarda farklı hash oluşturabilir. Bunun
nedeni hashleme sırasında rastgele salt kullanılmasıdır. Login sırasında
hash geri çözülmez; `VerifyHashedPassword` ile girilen şifrenin hash ile
uyumlu olup olmadığı kontrol edilir.

UserDto içinde PasswordHash olmadığı için GET cevaplarında hash dışarı
verilmez.


13. VALIDATION - ÜÇ AŞAMALI DOĞRULAMA
-------------------------------------

1. Model validation

Request modellerindeki Data Annotation attribute'ları çalışır:

- [Required]: alan boş olamaz.
- [EmailAddress]: email formatını kontrol eder.
- [StringLength]: karakter sınırını kontrol eder.
- [Range]: Page ve PageSize sınırlarını kontrol eder.
- [MaxLength]: Search uzunluğunu kontrol eder.

`[ApiController]` sayesinde geçersiz model controller metoduna girmeden
400 döner. Program.cs içindeki InvalidModelStateResponseFactory bu
hatayı sade bir JSON'a çevirir:

{
  "message": "Geçerli bir email adresi girilmelidir."
}

JSON'da eksik virgül, fazla virgül, tırnak veya parantez hatası varsa:

{
  "message": "JSON formatı geçersiz. Virgül, tırnak ve parantezleri kontrol edin."
}

2. Service / iş kuralı validation

- Email küçük harfe çevrilip normalize edilir.
- Aynı email daha önce kullanılmış mı kontrol edilir.
- String ID, Guid.TryParse ile doğrulanır.
- Kullanıcı bulunuyor mu kontrol edilir.
- Login email ve şifresi doğrulanır.

3. Database validation

AppDbContext içinde:

- Name NOT NULL, en fazla 100 karakter.
- Email NOT NULL, en fazla 254 karakter ve UNIQUE.
- PasswordHash NOT NULL, en fazla 500 karakter.
- UserType NOT NULL, en fazla 50 karakter ve default User.
- Id primary key.

Model validation kullanıcıya hızlı ve anlaşılır hata verir. Service
validation iş kurallarını korur. Database kısıtları ise son güvenlik
katmanıdır; API dışından veri yazılmaya çalışılsa bile tabloyu korur.


14. HATA YÖNETİMİ VE HTTP KODLARI
---------------------------------

UserService ve AuthService anlamlı exception üretir. Controller içine
tekrar tekrar try/catch yazılmaz. GlobalExceptionHandler bütün hataları
tek yerde aşağıdaki gibi çevirir:

- BadRequestException       -> 400 Bad Request
- UnauthorizedException     -> 401 Unauthorized
- NotFoundException         -> 404 Not Found
- ConflictException         -> 409 Conflict
- Beklenmeyen exception      -> 500 Internal Server Error

Ortak hata formatı:

{
  "message": "Hatanın anlaşılır açıklaması"
}

Temel başarı kodları:

- 200 OK: GET, PUT, login veya validate başarılı.
- 201 Created: kullanıcı başarıyla oluşturuldu.
- 204 No Content: kullanıcı başarıyla silindi.


15. ENTITY FRAMEWORK CORE, ENTITY, CONTEXT VE CODE FIRST
--------------------------------------------------------

Entity Framework Core, C# nesneleriyle veritabanı işlemi yapmamızı
sağlayan ORM aracıdır. Çoğu durumda elle SQL yazmak yerine LINQ ve
DbContext kullanılır.

Entity, veritabanı tablosunu temsil eden C# sınıfıdır. User entity'si
Users tablosunun Id, Name, Email, PasswordHash ve UserType kolonlarını
temsil eder.

AppDbContext, uygulama ile PostgreSQL arasındaki oturumdur. DbSet<User>
Users tablosuna erişmemizi sağlar. OnModelCreating kolon, index,
required, uzunluk ve seed data kurallarını tanımlar.

Code First, önce C# entity ve kurallarını yazıp veritabanı şemasını
migration ile bu koda göre oluşturmaktır.


16. MIGRATION NEDİR?
--------------------

Migration, modelde yapılan veritabanı yapısı değişikliğinin sürümlenmiş
C# kaydıdır. Migration dosyası tablo veya kolon değişimini tarif eder;
veritabanı ancak `database update` çalışınca güncellenir.

Projede bulunan temel migrationlar:

- InitialCreate: Users tablosunu ve ilk seed kayıtları oluşturdu.
- AddKaanSeedUser: Kaan seed kaydını ekledi.
- AddPasswordHashAndUserType: PasswordHash ve UserType kolonlarını ekledi.

Yeni migration örneği:

    dotnet tool run dotnet-ef migrations add MigrationAdi
    dotnet tool run dotnet-ef database update

`__EFMigrationsHistory` tablosu hangi migrationların veritabanına
uygulandığını tutar.


17. EF CORE METOTLARI NEDEN KULLANILDI?
---------------------------------------

FirstOrDefaultAsync
    Koşula uyan ilk kaydı getirir. Kayıt yoksa exception atmak yerine
    null döndürür; biz null durumunda 404 üretiyoruz.

AnyAsync
    En az bir kayıt var mı diye kontrol eder. Duplicate email kontrolünde
    bütün kaydı getirmekten daha uygundur.

CountAsync
    Arama filtresine uyan toplam kayıt sayısını SQL tarafında hesaplar.

AsNoTracking
    Salt okunur GET sorgularında EF'nin değişiklik takibi yapmasını
    engeller ve gereksiz maliyeti azaltır.

Add
    Yeni entity'yi EF'nin ekleme takibine alır.

Remove
    Entity'yi silinmek üzere işaretler.

SaveChangesAsync
    Add, update veya Remove ile bellekte takip edilen değişiklikleri
    gerçekten PostgreSQL'e gönderir. Çağrılmazsa değişiklik kalıcı olmaz.

Select
    Entity'den yalnızca dışarıya açılacak UserDto alanlarını seçer.

ToListAsync
    Hazırlanan sorguyu çalıştırıp sonuçları listeye çevirir.

Neden async?
    Veritabanı ve ağ işlemlerinde cevap beklenirken thread'i gereksiz
    bloke etmez. Uygulama başka isteklerle ilgilenebilir. Bu nedenle
    metodlar Task döndürür ve `await` kullanır.


18. PAGINATION VE SEARCH NASIL ÇALIŞIYOR?
-----------------------------------------

Örnek URL:

    /api/User?Page=2&PageSize=2&Search=kaan

Model binding URL'deki Page, PageSize ve Search değerlerini otomatik
olarak UserListQuery nesnesine çevirir.

UserService içindeki işlem sırası:

1. `_context.Users.AsNoTracking()` ile IQueryable oluşturulur.
2. Search doluysa Name veya Email için PostgreSQL ILIKE filtresi eklenir.
3. CountAsync ile filtreye uyan toplam kayıt sayısı bulunur.
4. Toplam sayfa sayısı hesaplanır.
5. OrderBy(Name).ThenBy(Id) ile kararlı sıralama yapılır.
6. Skip ile önceki sayfalardaki kayıtlar atlanır.
7. Take ile yalnızca istenen sayfa büyüklüğü alınır.
8. Select ile UserDto oluşturulur.
9. Sonuç PagedResponse içinde dönülür.

`ThenBy(Id)` önemlidir. Aynı ada sahip kayıtlar olduğunda yalnızca Name
ile sıralama kararlı olmayabilir ve aynı kayıt farklı sayfalarda tekrar
görülebilir.

Sınırlar:

- Page en az 1.
- PageSize 1 ile 100 arasında.
- Search en fazla 100 karakter.
- Sonuç bulunmazsa 404 değil, 200 ve boş items listesi döner.
- Var olmayan yüksek bir sayfa da 200 ve boş items listesi döner.


19. MODEL BINDING VE REQUEST BODY
---------------------------------

Model binding, HTTP isteğindeki URL, query string, route ve JSON body
değerlerini C# parametre veya model nesnesine çevirir.

Örnekler:

    [FromQuery] UserListQuery query
        Page, PageSize ve Search URL query stringinden gelir.

    [FromBody] UserCreateModel model
        Name, Email ve Password JSON request body'den gelir.

    [HttpGet("{id}")] ve GetById(string id)
        id route içinden gelir.

GET isteklerinde normalde request body kullanılmaz. GET veri okumak
içindir; filtre ve kimlik bilgileri route veya query string ile verilir.
Birçok istemci, proxy ve cache GET body'yi güvenilir biçimde işlemez.

POST ve PUT genellikle JSON request body kullanır. DELETE bu projede
silinen kaydı route ID ile belirlediği için body kullanmaz.


20. SWAGGER VE XML AÇIKLAMALARI
-------------------------------

Swagger, endpointleri tarayıcıda gösteren ve deneyebildiğimiz API
dokümantasyon ekranıdır. OpenAPI ise bu dokümanın standardıdır.

Controller ve modellerdeki `/// <summary>`, `<param>`, `<returns>`,
`<response>` ve `<example>` XML yorumları build sırasında XML dosyasına
yazılır.

StajApi.csproj içindeki:

    <GenerateDocumentationFile>true</GenerateDocumentationFile>

XML belgesini üretir. Program.cs içindeki:

    options.IncludeXmlComments(xmlPath);

bu XML açıklamalarını Swagger'a ekler.

`ProducesResponseType`, endpointin hangi HTTP kodunda hangi response
modelini döndürdüğünü Swagger'a bildirir.

Swagger üzerindeki Authorize düğmesinde login'den alınan JWT girilerek
korumalı validate endpointi test edilir.


21. POSTMAN KOLEKSİYONUNU İÇE AKTARMA
------------------------------------

Postman açılır:

1. Import seçilir.
2. `postman/StajApi.postman_collection.json` dosyası seçilir.
3. `StajApi - User ve JWT İşlemleri` koleksiyonu gelir.

Koleksiyon değişkenleri:

- baseUrl: http://localhost:5039
- userId: işlemlerde kullanılan kullanıcının GUID değeri
- userEmail: create/login için email
- userPassword: create/login için düz test şifresi
- jwtToken: login test scripti tarafından otomatik doldurulur

Hazır istekler:

1 - User List (GET)
1A - User Pagination (GET)
1B - User Search (GET)
1C - Geçersiz Pagination (GET 400)
2 - User Tekil Get (GET)
3 - Geçersiz GUID Hatası (GET 400)
4 - User Create (POST)
5 - User Update Name (PUT)
6 - Login ve JWT Al (POST)
7 - JWT Validate ve Claimleri Getir (GET)
8 - User Delete (DELETE)

İsteklerin test scriptleri beklenen status kodlarını ve bazı response
alanlarını otomatik kontrol eder. Create başarılı olunca dönen GUID
`userId` değişkenine, login başarılı olunca JWT `jwtToken` değişkenine
yazılır. Bu yüzden sonraki istekler hazır çalışır.


22. ÖNERİLEN POSTMAN TEST SIRASI
-------------------------------

API ve Docker çalışırken şu sıra izlenebilir:

1.  1 - User List                    -> 200

27. SIK KARŞILAŞILAN HATALAR
----------------------------

API başlamıyor, Jwt:Key boş hatası:
    appsettings.Local.json oluştur ve en az 32 karakterlik key yaz.

PostgreSQL connection refused:
    Docker Desktop ve staj-postgres-1 container'ını çalıştır. Portun
    5432 olduğunu kontrol et.

Password authentication failed:
    Docker'daki PostgreSQL şifresi ile appsettings.Local.json içindeki
    Password aynı değil.

Relation "Users" does not exist:
    Migration uygulanmamış olabilir. `database update` çalıştır.

Swagger Fetch error:
    Terminalde gerçek exception'a bak. Önce build al, API'yi yeniden
    başlat ve /swagger/v1/swagger.json adresini kontrol et.

400 JSON formatı geçersiz:
    Alanlar arasında virgül olduğuna, son alandan sonra gereksiz virgül
    olmadığına, tırnak ve parantezlerin kapandığına bak.

400 geçersiz GUID:
    ID tam GUID formatında olmalıdır. Örnek:
    11111111-1111-1111-1111-111111111111

401 Unauthorized:
    Login bilgileri yanlış olabilir. Validate için Authorization header
    eksik, token hatalı veya süresi geçmiş olabilir.

409 Conflict:
    Aynı email ile kullanıcı zaten vardır. Farklı email kullan.

404 Not Found:
    GUID formatı doğrudur fakat bu ID ile kayıt yoktur veya kayıt daha
    önce silinmiştir.

Kod değişti ama sonuç değişmedi:
    API'yi Control + C ile kapat, `dotnet build` ve `dotnet run` ile
    yeniden başlat.
